About

Hackerly

A hackathon platform: discovery and participation for hackers, operations for organizers, a focused review workspace for judges. One identity system, one database, one set of rules — three different ways of using it.

What it does

A hacker can find a hackathon, read it, register, join or create a team, build a project and submit it before a deadline the server enforces. An organizer can create a hackathon, brand it, set dates and prizes, define tracks and submission fields, publish a weighted rubric, invite judges, assign projects, watch judging progress, compute results and publish them. A judge can sign in, see their assignments, open a project, score it against the rubric, explain the score, submit, and move to the next one.

How judging works

Each review is converted to a 0–100 score using the organizer’s rubric weights. A project’s score is the mean of its submitted reviews. That is the whole default method, and it is what judging_mode = raw means.

With judging_mode = normalized, two extra steps run. First, each judge’s mean deviation from the panel mean is measured, and a project’s score is shifted by λ times the average offset of the judges who reviewed it. λ = 0 removes nothing; λ = 1 removes the full panel-difficulty effect. Second, the adjusted scores are min–max scaled to 0–100 inside each track, because two tracks can have very different score distributions and one should not dominate the other.

The method is deliberately conservative and fully deterministic. It is not a claim of statistical superiority, and it is not validated against any external ground truth. What it does guarantee: identical scores, a single reviewer, missing reviews, uneven judge workloads, zero variance and exact ties all produce a defined, explainable output. Ties share a rank and the next rank is skipped, and ties break deterministically on review count then project title, so the same input always yields the same ordering.

See JUDGING.md in the repository for the full specification and its limits.

Self-hosting

git clone https://github.com/your-org/hackerly
cd hackerly
docker compose up --build

That brings up a working portal on port 8080 with the schema created, the DOGFOOD fixtures loaded and a small demo set seeded. The database is a SQLite file in a volume, so nothing depends on an external service and the core product keeps working with the network off. Copy .env.example to .env to change anything.

Architecture in one paragraph

A single Node.js process serves the server-rendered UI and the JSON API. The browser never writes to the database; every mutation goes through a service that checks the session, the role, the event, the assignment and the deadline. Storage sits behind a driver interface with two implementations: SQLite for self-hosted installs, Firestore for a deployment on Google Cloud. Firebase Authentication is optional and only used to prove identity — Hackerly issues its own server-side session, so authorization never depends on a client-side role.

API

There is a small REST surface under /api/v1: published events, an event’s tracks and projects, creating an event, creating a submission, reading your own review scores, submitting a review, and organizer CSV export. It is documented in ARCHITECTURE.md.

Honest limits

  • Public voting and comments exist but have no moderation tooling beyond hiding a comment.
  • Normalization is optional and off by default. It is documented, not proven.
  • There is no email provider by default: judge invitations are written to data/outbox and shown in the organizer’s judge list, and the UI says so rather than claiming a message was sent.
  • Avatars are generated from a deterministic seed or set to an external HTTPS URL. There is no binary upload pipeline.
  • Scale claims are backed only by the load tests in scripts/loadtest.mjs, and their measured numbers are recorded in the README.
